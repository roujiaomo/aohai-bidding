## 一、计分公式文案改造（用户需求 1）

**操作**：「数据规则 → 一级规则」顶部说明文案替换为大白话，已部署上线。

**现文案**：
> 打分方法：一条公告的标题/采购单位/地区/正文中，某个分类的关键词命中得越多，这个分类给的分越高——命中 1 个词 +15 分、2 个词 +22 分、3 个词 +29 分，依此类推，但最多不超过该分类的权重（权重就是"这个分类最高能得多少分"）。所有命中分类的得分相加，再叠加下方的地区/采购方/预算加分，总分封顶 100。一个关键词都没命中 → 0 分，不入库。各分类权重相加不需要等于 100。

**结果**：✅ 页面已生效，原公式 `min(权重, 8 + 7×n)` 不再向用户展示。

### 2.3 代码修复（溯因后修改，均已部署）

1. **入库噪声闸**（新增 `_title_gate_ok`，挂载于 `upsert_tender`）——五层判定：

### 3.5 测试中发现并修复的新问题：去重兜底与跨阶段误合并

**发现过程**：
1. 抓后复审发现 4 组重复记录 → 溯因确认是**当天 08:00 定时任务（尚在旧去重代码下）入库的漏网记录**，用新代码跑 `find_duplicate` 全部正确命中，非新代码缺陷。
2. 为此新增**全局去重兜底** `sweep_duplicates`：每次抓取（API 与 CLI 两个入口）结束自动全库比对、合并重复对。
3. 首次运行兜底合并 12 条，核对明细时发现**过度合并**：同项目的"招标公告"被并进"中标公告"、"比选公告"被并进"比选结果公告"——这些是不同阶段的不同商机线索，必须各自独立。
4. **修复**：新增公告阶段分类器 `_notice_stage`（正则长词优先，取标题中最后出现的公告类型词；截断标题不参与模糊合并）；`find_duplicate` 与兜底均加"同阶段才可模糊合并"约束。
5. **回归验证**：恢复备份重跑，最终只合并 **5 条真重复**（全部精确同标题）；河北海事招标/中标、测评比选/比选结果、盘锦系列、链路招标/废标等跨阶段公告全部完整保留。复审 0 噪声 / 0 重复 / 0 零分，有效 227 条。
6. E2E 22 项在修复后**复测再次全过**。

## 六、遗留观察项（未改动）

1. **id=882**「长天龙起重机变幅钢丝绳换装工程项目公开招标公告」：score=30 但优先级为"重点关注"且无备注——疑似人工手动设置。系统策略不覆盖人工优先级，故保留不动，特此说明。
2. **手动抓取耗时约 25 分钟**：`POST /api/fetch` 为同步接口，用 curl 触发会超时看不到汇总返回，但不影响实际执行（结果以库内统计为准）。界面按钮触发不受影响。
3. **并发抓取**：定时任务与手动抓取若同时运行，理论上可能短暂产生重复入库，由抓取收尾的去重兜底自动收敛，无需人工处理。
