# 遨海商机雷达｜软件设计基线

> 版本：2026-08-25  
> 部署形态：单机、低配优先、Python 标准库 + SQLite + Nginx + systemd。  
> 本文描述当前已上线设计，不等同于未来重构目标。

## 1. 系统定位

遨海商机雷达用于从公开招投标渠道和天眼查官方授权通道发现商机，完成清洗、评分、去重、跟进与提醒。系统不下载标书、不执行报名投标、不绕过登录、验证码或反自动化措施。

## 2. 总体架构

```text
公开公告网站 / 天眼查官方 CLI
             │
             ▼
    Python 抓取适配器与清洗管线
             │
             ▼
 SQLite（WAL + FTS5 + 触发器）
             │
      ┌──────┴──────┐
      ▼             ▼
Python HTTP 服务   钉钉自定义机器人
ThreadingHTTPServer    定时 Markdown 提醒
      │
      ▼
 Nginx `/radar/` 反向代理
      │
      ▼
浏览器管理看板
```

## 3. 代码与模块职责

| 文件 | 职责 |
|---|---|
| `app/radar.py` | 主程序：数据库迁移、评分、去重、30 个抓取适配器、CLI、HTTP API、内嵌前端 |
| `app/radar_notify.py` | 钉钉 Markdown 通知、签名、实时商机筛选 |
| `config.json` | 可编辑的看板、筛选、保留期、业务关键词、区域、采购方规则 |
| `data/radar.db` | SQLite 主数据库 |
| `backup_radar.py` | 每日 SQLite 备份 |
| `docs/数据规则.md` | 数据规则和变更边界 |
| `docs/软件设计.md` | 当前软件结构和运行设计 |

前端页面以内嵌 HTML/CSS/JavaScript 形式保存在 `radar.py` 的 `INDEX_HTML` 中，不依赖 Node.js、Vue、React 或前端构建链路。

## 4. 运行时组件

### 4.1 Web 服务

- Python 3.11；
- `ThreadingHTTPServer` 监听 `127.0.0.1:8788`；
- systemd 服务：`bidding-radar.service`；
- Nginx 将 `http://39.96.217.93/radar/` 反向代理到该端口；
- 服务使用 `bidding` 用户运行，启用 `NoNewPrivileges=true`、`PrivateTmp=true`、`Restart=on-failure`。

### 4.2 数据库

SQLite 使用 WAL 模式，读看板与后台写入可并发进行。

| 表/对象 | 用途 |
|---|---|
| `sources` | 来源代码、名称、接入状态、最近检查/成功/错误时间 |
| `tenders` | 公告主体、评分、优先级、正文、来源、跟进、软删除与业务标签 |
| `buyer_profiles` | 天眼查采购方画像结果 |
| `tender_search` | FTS5 全文检索索引 |
| `tenders_ai` / `tenders_au` | 插入、更新时同步 FTS 索引的触发器 |

普通索引：`score DESC`、`deadline_at`。数据库启动时会执行兼容性迁移，补充新增列并处理旧版本表结构。

## 5. 抓取与入库设计

### 5.1 来源层

适配器覆盖公开 HTML、公开 JSON API、TRS/CMS 列表、官方聚合平台及天眼查官方 CLI。来源状态写入 `sources`，未自动化渠道保留原因，不规避反爬或登录限制。线上当前公告保留期为 365 天。

每个适配器输出统一字典：

```text
source_url, title, published_at, buyer, region, content, deadline_at（可选）, budget（可选）
```

### 5.2 通用抓取管线

```text
适配器列表
  → 可访问性检查（例外来源跳过 HEAD）
  → 详情页正文/截止日期补全
  → 组织、代理机构、中标单位提取
  → 评分和分类
  → 噪声闸
  → 指纹/相似标题去重
  → SQLite 入库或更新
  → 来源成功状态更新
```

抓取结束后执行超期清理和全库去重兜底。抓取失败会更新来源错误信息，但不会中断其他来源。

### 5.3 天眼查专用设计

天眼查通过 `tyc operation bids` 官方 CLI 调用，使用 OAuth 登录态；凭据不写入项目配置或数据库。

系统通过 `TYC_PROFILE` 选择关键、核心、扩展、延迟补偿四类任务。每页 100 条；仅满页时继续请求下一页。任务日志输出 profile、关键词、页码、返回量，便于审计索引延迟与额度消耗。

常规 `fetch` 不含 `tianyancha` 和 `ccgp_search`，两者由独立 timer 调度；但 `fetch tianyancha` 仍可作为显式人工命令执行兼容模式。

## 6. HTTP API 与前端

| API | 方法 | 功能 |
|---|---|---|
| `/` | GET | 内嵌看板页面 |
| `/api/stats`、`/api/history-stats` | GET | 实时/历史统计 |
| `/api/tenders`、`/api/history` | GET | 实时/历史列表、搜索、优先级筛选、分页 |
| `/api/sources` | GET | 来源状态 |
| `/api/rules` | GET / PUT | 读取、校验并保存可编辑规则 |
| `/api/deleted` | GET | 回收站 |
| `/api/fetch` | POST | 常规来源同步抓取 |
| `/api/tenders/*` | POST | 过期、优先级、软删、恢复 |
| `/api/config` | GET / POST | 配置读取和写入 |

实时列表按优先级、发布日期排序；历史列表按发布日期与 ID 倒序。搜索当前使用 `LIKE` 覆盖标题、采购方、地区、正文等字段；FTS5 已建立，可在数据量显著增长时接入查询层。

## 7. 定时任务

| Timer | 服务 | 计划 |
|---|---|---|
| `bidding-radar-fetch.timer` | 常规公开来源抓取 | 每 4 小时整点 |
| `bidding-radar-ccgp.timer` | 政采网关键词检索 | 每日 08:20、18:20 |
| `bidding-radar-backup.timer` | 数据库备份 | 每日 02:15 |
| `bidding-radar-tyc-critical.timer` | 天眼查关键层 | 每 4 小时 20 分 |
| `bidding-radar-tyc-core.timer` | 天眼查核心层 | 01:00、09:00、17:00 |
| `bidding-radar-tyc-expansion.timer` | 天眼查扩展层 | 每日 12:30 |
| `bidding-radar-tyc-delay-backfill.timer` | 天眼查延迟补偿 | 每日 13:15 |
| `bidding-radar-notify-morning.timer` | 钉钉实时汇总 | 每日 10:00 |
| `bidding-radar-notify-key.timer` | 钉钉重点复提醒 | 每日 14:00、20:00 |

全部 timer 使用 `Persistent=true`：服务器停机错过计划后，恢复时可补执行。

## 8. 钉钉提醒设计

- 凭据放在服务器 root-only 环境文件，不放入 `config.json`；
- 机器人请求采用时间戳 + HMAC-SHA256 签名；
- 10:00：有“值得跟进/重点关注”实时商机时推送；
- 14:00、20:00：有“重点关注”实时商机时推送；
- 按评分取前三条，展示优先级、标题、采购方、地区、截止时间、评分、原文链接；
- 底部固定提供看板链接；无符合条件公告时，正式任务不发送。

## 9. 已知约束与改进边界

1. SQLite 是单机单写模型；当前低并发适用，未来多用户频繁写入或并发抓取应迁移 PostgreSQL 并引入任务队列。
2. 抓取稳定性主要受外部网站页面、限流和索引延迟影响；不能以服务器资源替代来源监控。
3. 天眼查是聚合检索源，详情页、移动端、搜索接口的可见时间可能不同；延迟补偿任务用于降低而非消除该风险。
4. 当前 `/api/config` 对外暴露的范围应持续审查；任何凭据不得进入 `config.json`。
5. API 对非法数字参数目前可能返回 500，应在后续改造中改为 400。
6. 变更评分、去重、保留期、提醒条件前，必须同步更新 `docs/数据规则.md`，并增加对应测试用例。

## 10. 推荐变更流程

```text
需求确认
  → 更新数据规则文档
  → 编写/更新测试用例
  → 本地临时库验证
  → 备份线上数据库
  → 部署代码或 timer
  → 线上只读核验与日志观察
  → 更新软件设计文档与变更记录
```
